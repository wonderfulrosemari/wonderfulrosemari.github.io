OVERVIEW

프로젝트 개요

LUNO는 통화 음성과 문자 URL을 분석해 보이스피싱 위험도를 알려주는 Android 보안 서비스입니다. 대회 당시에는 STT 전사 텍스트를 중심으로 통화 위험을 분석하고 문자 URL을 공공 목록과 대조했습니다. 서비스 초기 신고 데이터가 비어 있으면 사용자가 조회 기능을 신뢰하기 어렵다고 판단해, 공공데이터의 스팸 번호를 DB에 미리 적재했습니다. 사용자 제보가 쌓이기 전에도 알려진 스팸 번호를 조회할 수 있도록 초기 데이터를 구성했습니다. 대회 이후에는 제가 발화 특성을 추가해 탐지 정확도를 개선했습니다.

PROBLEM & SOLUTION

문제 인식과 해결

기관 사칭과 취업 사기 문구는 육안으로 구분하기 어렵고, 문자 URL은 링크를 누르기 전 위험 여부를 확인하기 어렵습니다. 초기 텍스트 모델의 탐지 정확도는 약 86%였지만, 문맥과 발화 방식에서 드러나는 위험 신호가 충분히 반영되지 않았습니다.

  • 팀장으로서 금융감독원 보이스피싱 사례 약 140건을 다시 살펴 누락된 사례의 공통점을 찾고, 텍스트 분석만으로 포착하기 어려운 위험을 개선 과제로 정리했습니다.
  • 음성 입력 → CLOVA STT 전사 → AI 분석 → 위험도 결과로 처리 단계를 나누고, 앱·백엔드·AI 서버가 각 단계의 요청과 응답을 연결하도록 구성했습니다.
  • CLOVA STT 전사문을 SBERT 의미 유사도, 한국어 BERT 문맥 분류, Naive Bayes 분류 점수와 룰 기반 키워드 점수로 분석했습니다. 대회 이후에는 텍스트만으로 놓치기 쉬운 재촉·압박 양상을 보완하기 위해 발화 속도와 무음 구간을 추가하고, 텍스트 위험도와 음성 위험도를 가중합했습니다.
  • 보이스피싱 사례 약 140건에 정답 라벨을 붙여 예측 결과와 비교했습니다. 음성 특성을 보완한 뒤 내부 평가의 정답 일치율이 약 86%에서 92%로 개선됐습니다. 실제 서비스 환경 전체의 정확도를 보장하는 수치와는 구분했습니다.
  • 서비스 초기에 신고 DB가 비어 있어 조회 기능에 대한 신뢰가 낮아질 수 있다고 판단했습니다. 한국인터넷진흥원·과학기술정보통신부 제공 공공데이터의 스팸 번호를 미리 적재해, 제보가 없는 초기에도 알려진 번호를 조회할 수 있도록 구성했습니다.
  • 신고 이력이 없는 초기에도 문자 조회가 가능하도록 공공 URL 데이터를 기준 목록으로 활용했습니다. 이후 사용자 제보를 검토·축적해 조회 범위를 넓히는 방향으로 설계했습니다.

DATA FOUNDATION

스팸 번호·문자 URL 데이터와 조회 흐름

초기 데이터 · 스팸 번호 사전 적재
사용자가 처음 접속했을 때 데이터가 없는 서비스로 느끼지 않도록 공공데이터의 스팸 번호를 DB에 미리 적재했습니다. 번호 사전 적재와 문자 URL 대조를 구분해, 신고 데이터가 축적되기 전에도 알려진 위험 정보를 확인할 수 있도록 했습니다.
초기 데이터 · 공공 URL 목록
서비스를 처음 시작할 때는 사용자 신고 데이터가 없었습니다. 공공데이터로 공개된 피싱·스미싱 URL 목록을 초기 조회 기준으로 삼아, 제보가 쌓이기 전에도 알려진 위험 링크를 확인할 수 있도록 했습니다.
서비스 적용 · URL 대조
기존 백엔드는 요청에 포함된 URL 목록을 phishing_url 테이블에서 조건 조회했습니다. 후속 작업에서는 유효한 메모리 스냅샷이 있으면 Set의 포함 여부로 검사하고, 스냅샷이 없거나 오래됐으면 DB 조회로 전환하도록 구성했습니다. 문장 전체를 분류하는 음성 AI와는 별도의 목록 기반 검사입니다.
확장 방향 · 사용자 제보 축적
공공 목록을 시작점으로 두고, 사용자 제보를 접수한 뒤 중복 제거와 관리자 검증을 거쳐 조회 데이터에 반영하는 흐름을 구상했습니다. 검증된 제보가 쌓이면서 새로운 스팸문자와 피싱 URL까지 조회 범위를 넓히는 방향입니다.

ARCHITECTURE

아키텍처

  • Android 앱이 분석 요청과 결과 조회를 담당하고, Spring Boot가 인증·분석 이력·API를 처리합니다.
  • 음성 파일은 Firebase Storage에 저장한 뒤 CLOVA STT 전사와 FastAPI 추론을 거쳐 결과를 반환합니다. Spring Boot는 사용자·인증·분석 이력을 관리합니다.
  • 문자 URL은 공공 URL 목록과 대조하고 신고·분석 정보는 MySQL에 저장합니다. Redis의 토큰·조회 처리와 별도로, 후속 로컬 개선에서 URL 목록의 불변 Set 기반 Snapshot Cache와 DB 대체 조회를 적용했습니다.
  • 분석 요청의 지연·오류와 STT·AI 의존성 상태는 Prometheus 메트릭과 구조화 로그로 수집하고, Grafana에서 운영 상태를 확인할 수 있게 구성했습니다.

AFTER THE COMPETITION

대회 이후 개선

대회 당시에는 음성 특성을 반영하지 못했습니다. 수상 이후에도 실제 피해 예방에 도움이 되는 서비스로 개선하고 싶어, 발화 속도와 무음 구간을 직접 추가하고 텍스트 위험도와 음성 위험도를 결합했습니다. 금융감독원 사례 약 140건의 정답 라벨과 예측 결과를 비교한 내부 평가에서 정답 일치율이 약 86%에서 92%로 높아졌습니다. 별도 검증 데이터의 구성이나 실서비스 전체의 정확도를 입증한 수치로 확대하지 않았습니다.

OPERATIONAL IMPROVEMENT

조회 구조 개선과 타임아웃 진단·재검증

모델 정확도 개선과 별도로, 문자 URL 검사 경로의 DB 의존을 줄이고 로컬 부하테스트에서 발생한 간헐적 타임아웃을 진단했습니다. 조회 구조 개선과 실행 환경 변경의 결과를 구분해 검증했습니다.

조회 구조 · 불변 Set 기반 Snapshot Cache
기존에는 요청마다 입력 URL 목록을 findByUrlIn()으로 조건 조회했습니다. 유효한 스냅샷이 있으면 메모리 Set에서 URL 포함 여부를 확인해 요청별 Repository 조회를 생략하도록 변경했습니다. 캐시 조회와 DB 대체 조회 동작은 mock 서비스 테스트 2건으로 확인했습니다.
최신성과 장애 대응 · 주기 갱신과 DB 대체 조회
갱신 완료 후 30초 간격으로 목록을 다시 읽고, 마지막 성공 갱신 후 2분을 넘겼거나 스냅샷이 없으면 DB를 조회합니다. 갱신 실패 시 허용 시간까지 기존 스냅샷을 유지하며, 목록 상한 100,000개를 넘으면 캐시를 비워 메모리 사용을 제한합니다. 유효한 스냅샷에 없는 새 URL은 다음 갱신까지 반영이 지연될 수 있어 조회 감소와 최신성의 절충을 고려했습니다.
관찰 · Prometheus·Grafana·Loki/Alloy·Alertmanager
요청량·지연·오류·자원 포화를 Golden Signals, RED, USE 관점으로 확인했습니다. 조회 경로·캐시 갱신·CPU·Hikari 연결 풀 지표와 로그를 연결하고, 로그 수집과 장애 알림을 구성했습니다. SMS p95가 약 2ms여도 일부 요청이 5초 타임아웃으로 실패하는 상황을 확인해, 요청 전체 시간·연결 대기·실패별 오류 로그까지 진단을 보강했습니다.
캐시 전후 비교 · 효과와 한계 구분
SMS 단독의 단계별 10초 비교에서는 캐시 ON의 p95가 낮게 관찰됐지만, 단계별 60초 혼합 시험에서는 결과가 일관되지 않았고 캐시 ON 재시험에서도 HTTP 실패 34건이 발생했습니다. 캐시가 타임아웃을 해결했다고 결론 내리지 않고 조회 우회 동작과 지연·실패의 변화를 구분했습니다. 실행 당시 모든 변수의 통제나 실제 SQL 총량 측정은 확인되지 않아 지속적 성능 개선율과 DB 조회 감소율을 주장하지 않았습니다.
진단과 조치 · Docker/native 실행 환경 비교
1,000 RPS의 Docker k6 진단에서 60,002건 중 타임아웃 14건을 확인했습니다. 수집된 CPU·DB 풀 지표로 지속적인 포화를 단정할 수 없어 통신 경로도 비교했습니다. IPv4 주소로 바꿔도 타임아웃 49건이 발생해 같은 k6 버전의 Mac 직접 실행으로 전환했습니다. 백엔드 코드·DB 풀·캐시 ON·요청 구성·부하는 유지했고, SMS 5초·AI 8초 제한을 늘리거나 재시도를 추가하지 않았습니다. 실행 환경·버전·스크립트 해시와 실패별 진단 로그를 남기되 요청 본문과 인증 헤더는 저장하지 않았습니다.
반복 검증 · 독립 60초 3회와 5분 연속 시험
서로 겹치지 않는 1,000 RPS 시험을 수행해 총 480,007건의 HTTP 요청에서 실패와 미실행 반복(dropped iterations) 0건을 확인했습니다. 판정 기준과 진단 기록을 확인하는 테스트 4건도 통과했습니다. 캐시 ON은 전후 동일했으므로 이 결과를 캐시가 타임아웃을 해결한 성과로 귀속하지 않았습니다.

검증 조건: H2 메모리 DB, 테스트 URL 3개, SMS 약 70%·대체 로컬 AI 약 30%. 요청 수에는 health 확인이 포함됩니다. 실제 STT·Firebase·운영 MySQL이나 서버 최대 처리량을 검증한 결과는 아닙니다. Docker 내부의 정확한 원인과 캐시의 타임아웃 해결 효과는 확정하지 않았습니다.
